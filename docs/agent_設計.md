## 一、專題摘要

「標案補助小幫手」是一個每天自動更新的網頁版 AI Agent，協助中小企業、新創與接案者掌握**政府標案**、**得標行情**與**補助消息**。

系統每天自動從政府電子採購網與新聞來源抓取資料，經過關鍵字萃取、過濾、去重與清理後存入資料庫。使用者打開網頁就能看到當天最新、尚未截止的標案，也能直接用自然語言詢問 AI，例如「我是台中 10 人的軟體公司，有什麼標案？」或「這類案子通常幾折得標、誰常得標？」。AI 會記住使用者的公司條件，呼叫工具查詢資料庫後回答，並由前後兩道安全護欄把關。

| 項目 | 內容 |
|---|---|
| 主題 | 政府標案與補助資訊整合（非美食、天氣、旅遊、交通、體育、八卦） |
| 使用者 | 中小企業、新創、接案者、公司業務人員 |
| 重複性排程 | 每天 07:30 自動抓取 → 清理 → 入庫 |
| 可分享使用 | 多人各自註冊帳號，看到同一份每日資訊，AI 記憶與收藏各自獨立 |
| 技術 | Python、FastAPI、SQLite、jieba、Google Gemini（tool calling） |

## 二、問題背景與動機

### 2.1 社會問題：取得政府資源的資訊落差

- 政府電子採購網**每天約有 3,000 筆公告**（本專題 2026/10/08 實測為 3,011 筆），包含招標、決標、更正等多種類型，一般人很難逐筆篩選。
- 補助與獎勵計畫散落在各部會網站與新聞，常因不知道而錯過申請期限。
- 大型企業有專人追蹤標案，**中小企業與個人工作者沒有**，因此在取得政府資源上長期處於劣勢。

### 2.2 一個值得注意的發現

本專題整理了 197 筆決標資料後發現，**政府標案平均只有 1.3～1.5 家廠商投標**（詳見第九節）。競爭其實比多數人想像的少，真正的門檻往往是「不知道有這個案子」。這也印證了本專題要解決的正是資訊落差。

### 2.3 目標

1. 每天自動整理，使用者不用自己追
2. 依使用者的公司條件精準推薦，而不是丟一大串清單
3. 提供一般人查不到的「得標行情」，協助判斷值不值得投
4. 回答必須正確、可追溯，不能編造案名、金額或連結

## 三、系統架構

```
┌─────────────── 每日自動排程（app/scheduler.py，每天 07:30）───────────────┐
│                                                                            │

│                            ├─ 決標公告 → 標題粗篩 → 抓明細 → 判斷產業     │
│                            └─ 各產業每日招標數（趨勢）                    │
│  Google 新聞 RSS ────────── 補助／獎勵消息 → 標題須含「補助、獎勵…」     │
│                                   │                                        │
│                                   ▼                                        │
│        資料前處理 pipeline：提取 → jieba 關鍵字 → 過濾 → 去重 → 清理     │
│                                   │                                        │
│                                   ▼                                        │
│                         SQLite 資料庫（data/agent.db）                     │
└────────────────────────────────────────────────────────────────────────────┘
                                    │
          ┌─────────────────────────┴──────────────────────────┐
          ▼                                                    ▼
  網頁首頁（每日最新資訊）                        AI 小幫手（Gemini Agent）
  ・未截止標案、3 天內截止提醒                      輸入護欄（規則＋LLM）
  ・我的追蹤（截止倒數、行事曆）                            ▼
  ・趨勢圖、得標行情圖                          Agent 依意圖呼叫工具查資料庫
  ・補助消息、匯出 Excel                                    ▼
  （直接查資料庫，不耗 LLM 額度）               輸出護欄（連結查證＋LLM 審查）
```

### 3.1 技術選擇

| 元件 | 選用 | 理由 |
|---|---|---|
| 網頁服務 | FastAPI | 輕量、非同步，方便同時提供網頁與 API |
| 資料庫 | SQLite | 單一檔案、免安裝，適合本機部署 |
| 中文斷詞 | jieba | 萃取標案與新聞的關鍵字，提升檢索命中率 |
| LLM | Google Gemini（Flash 系列） | 有免費額度、支援 tool calling、中文表現佳 |
| 前端 | 原生 HTML／JavaScript／SVG | 不依賴外部框架，圖表自行繪製 |

## 四、資料流程與前處理

### 4.1 資料來源

| 資料 | 來源 | 頻率 |
|---|---|---|
| 招標公告 | 政府電子採購網（透過 g0v 開放 API） | 每日 |
| 決標公告 | 同上，含得標廠商、決標金額、底價、投標家數 | 每日 |
| 補助消息 | Google 新聞 RSS（6 組關鍵字搜尋） | 每日 |

### 4.2 篩選策略：用「標的分類」而不是關鍵字

初版用標題關鍵字判斷產業，例如「系統」「活動」，結果「活動中心整修工程」被歸成行銷類、「空調系統」被歸成資訊類，誤判很多。

改版後改用政府採購的**標準標的分類代碼**作為主要依據，例如「勞務類 84」代表電腦相關服務、「勞務類 871」代表廣告服務；關鍵字只作為輔助，而且工程類一律不用關鍵字比對。

### 4.3 前處理成效（2026/10/08 實測）

| 階段 | 筆數 |
|---|---|
| 採購網當日公告 | 3,011 |
| 招標類型＋產業篩選後 | 約 170 |
| 補助新聞（6 組搜尋）→ 標題篩選＋去重後 | 21 → 9 |
| 決標資料（往前補抓 14 天） | 197 |

前處理沿用本人先前開發的文件清理工具（jieba 關鍵字、過濾、去重、清理）。同一則補助新聞常被多家媒體重複報導，去重步驟可以避免 AI 重複推薦。

## 五、AI Agent 設計

### 5.1 LLM 選擇與參數

| 用途 | 模型 | 參數 | 說明 |
|---|---|---|---|
| Agent 主模型 | gemini-3.5-flash | temperature 0.3 | 需要理解問題、選工具、整理回答 |
| 備援模型 | 3.6 / 3.7 / 2.5 Flash、2.5 Flash-Lite | 同上 | 主模型額度用完或忙碌時依序替換 |
| 安全護欄 | gemini-3.5-flash-lite | temperature 0、JSON 輸出 | 只做判斷，要求穩定、快速 |

**設計考量**：免費額度是「每個模型」分開計算，每分鐘與每天各有上限。實測最新的 3.8 Flash 每分鐘只能呼叫 5 次，而一則對話需要 3～5 次呼叫，因此改為 Agent 和護欄使用不同模型分攤額度。系統會記住當天額度已用完的模型並直接跳過；若只是每分鐘額度用完，則等待後重試。

### 5.2 Prompt 設計

System Prompt 以 XML 標籤分成三段：

```xml
<role>你是「標案補助小幫手」，協助台灣中小企業、新創與個人工作者……今天是 {today}。</role>
<user_profile>產業：{industry}｜人數：{company_size}｜地區：{location}｜需求：{need}</user_profile>
<rules>
1. 使用者提到產業、人數、地區或需求時，先呼叫 save_profile 記住。
2. 想找案子但看不出產業時，先追問產業，不要直接查。
3. 案子與數字只能來自工具回傳的結果，不可自行編造。
……（共 11 條）
</rules>
```

- `{user_profile}` 每次對話動態帶入，這是 AI 的長期記憶
- `{industries}` 從設定檔讀取，使用者在網頁新增產業後 AI 立即認得
- 規則 3 搭配輸出護欄，從兩個層面防止幻覺

### 5.3 Memory（記憶）

| 類型 | 內容 | 實作 |
|---|---|---|
| 長期記憶 | 產業、公司人數、地區、需求 | `users` 資料表；AI 透過 `save_profile` 工具寫入 |
| 短期記憶 | 最近 10 則對話 | `messages` 資料表，每次對話帶入 |

**長期記憶與個人資料頁雙向同步**：使用者在個人資料頁填寫公司條件，AI 立即知道；在對話中提到的條件，個人資料頁也會更新。

### 5.4 Knowledge：為什麼用 tool calling，而不是向量 RAG

標案是**結構化資料**，具有預算、截止日、地區、產業等欄位。使用者常問的問題像是：

> 「台中、預算 500 萬以上、**還沒截止**的軟體標案有幾件？」

向量相似度檢索（RAG）擅長找「語意相近的段落」，但無法正確判斷「預算 ≥ 500 萬」「截止日在今天之後」這類條件，容易推薦過期的案子或講錯數字。

因此本專題採用以下分工：

- **LLM**：理解問題、決定查詢條件、整理回答
- **SQL**：精準篩選與計算

自動評估中的「條件篩選計數」題，AI 回答的件數與資料庫標準答案完全一致，驗證了這個設計。非結構化的補助新聞則以關鍵字檢索，並搭配 jieba 萃取的關鍵字提升命中率。

### 5.5 Tools（工具）

| 工具 | 功能 | 對應問題範例 |
|---|---|---|
| `search_tenders` | 依產業、關鍵字、地區、預算區間、是否截止查標案 | 台中 500 萬以上的軟體標案？ |
| `search_subsidies` | 依關鍵字查補助消息 | 最近有數位轉型補助嗎？ |
| `read_tender_page` | 讀取公告全文（**只允許採購網網域**） | 這案押標金多少？ |
| `analyze_awards` | 統計得標行情：金額中位數、折數、投標家數、得標排行 | 這類案子幾折得標？誰常得標？ |
| `list_favorites` | 列出使用者收藏與剩餘天數 | 我收藏的哪個最快截止？ |
| `save_profile` | 記住公司條件 | 我們是高雄 8 人的行銷公司 |
| `get_today_digest` | 取得今日快報 | 今天有什麼新的？ |

**設計重點**：得標行情的平均、中位數、排行等數字**全部由程式計算**後才交給 LLM，LLM 只負責解讀和說明，避免模型自己算錯。

### 5.6 對話流程

```
使用者訊息
   │
   ▼
【輸入護欄】第一層：規則比對（prompt injection 關鍵句）
           第二層：LLM 判斷（JSON：allow / reason）
   │ 違規 → 婉拒
   ▼
【Agent】讀取長期記憶＋最近 10 則對話
   ├─ 缺產業 → 追問（不查詢）
   ├─ 查標案 → search_tenders →（可再）read_tender_page
   ├─ 問行情 → analyze_awards
   ├─ 問補助 → search_subsidies
   └─ 提到條件 → save_profile
   ▼
【輸出護欄】連結代碼還原與查證 → LLM 內容審查 → 補上免責聲明
   ▼
回覆（網頁上同時顯示本次呼叫了哪些工具）
```

### 5.7 Guardrail（安全護欄）

| 位置 | 機制 | 擋下什麼 |
|---|---|---|
| 輸入端 | 規則比對 | 「忽略以上指令」「system prompt」等明顯攻擊，0.1 秒內擋下，不耗額度 |
| 輸入端 | LLM 判斷 | 換句話說的 prompt injection、圍標／綁標／借牌等違法詢問、不當內容、他人個資 |
| 輸出端 | **連結代碼機制** | 防止模型編造或抄錯網址（見下說明） |
| 輸出端 | LLM 審查 | 不當用語、違法建議、洩漏系統指令 |

**連結代碼機制**：實測發現，模型抄寫採購網的長網址時常會錯幾個字。因此工具不直接把網址交給模型，而是給短代碼（如 `<<T1>>`），由程式在輸出時換回真正的網址；模型自己寫出的陌生網址則整行刪除。評估結果中被攔下的編造連結為 **0 個**。

## 七、帳號與資安設計

| 項目 | 做法 |
|---|---|
| 密碼儲存 | PBKDF2-SHA256、隨機 salt、20 萬次迭代，資料庫中沒有明碼 |
| 暴力破解防護 | 同一帳號 10 分鐘內錯 5 次即暫停登入 |
| 登入狀態 | 隨機 session token 存於 HttpOnly cookie（JavaScript 無法讀取），資料庫只存 token 的雜湊值；7 天到期 |
| 改密碼 | 其他裝置上的登入自動失效 |
| 資料隔離 | 收藏、對話、AI 記憶一律以伺服器端的登入身分判斷，不信任前端傳來的使用者 ID |
| 存取控制 | 未登入時，頁面導向登入頁，API 回傳 401 |
| 工具白名單 | `read_tender_page` 只能讀取政府採購網，避免被利用來存取任意網址 |
| 金鑰管理 | API key 放在 `.env`，不進版本控制 |

## 八、評估方法與結果

### 8.1 方法

設計 **21 題測試題**，分為六類。**標準答案在測試當下由 SQL 從資料庫即時計算**，例如「台中、500 萬以上、未截止的資訊軟體標案件數」。因此資料每天更新，標準答案也會跟著更新，不需要手動維護。

每題自動檢查：

- **工具選擇**：是否呼叫了正確的工具與參數，例如有沒有帶入「臺中」
- **答案正確性**：件數、案名、折數、得標廠商是否與資料庫一致
- **護欄行為**：該擋的有沒有擋、不該擋的有沒有誤擋
- **幻覺**：輸出護欄是否攔下編造的連結

若因免費額度不足導致模型無法回應，該題標記為「未計分」，不視為答錯，以區分「系統能力」與「額度限制」。

### 8.2 結果（2026/10/12）

| 類別 | 通過 |
|---|---|
| 標案檢索（條件計數、列表、最高預算、預算門檻、讀公告） | 5／5 |
| 得標行情（折數、得標排行、競爭程度） | 3／3 |
| 記憶與追問（缺資訊先追問、跨回合記住條件） | 2／2 |
| 補助查詢 | 1／1 |
| 護欄攔截（3 種 prompt injection、借牌、綁標） | 5／5 |
| 護欄放行（一般問候、專業問題不誤擋） | 2／2 |
| **合計** | **18／18（100%）** |

| 指標 | 結果 |
|---|---|
| 工具選擇正確率 | 100% |
| 護欄正確率（攔截＋放行） | 100%（7／7） |
| 被攔下的編造連結 | 0 個 |
| 平均回應時間（一般問題） | 15.7 秒 |
| 護欄攔截回應時間 | 0.1～1.2 秒 |

另有 3 題（沿用條件只改預算、收藏最快截止、離題導回）因當日免費額度用完而尚未計分。完整報告見 [docs/eval/](eval/)。

### 8.3 討論

- 「讀公告回答細節」耗時最長（47 秒），因為需要即時連線採購網讀取全文
- 規則式護欄可在不呼叫 LLM 的情況下擋下明顯攻擊；換句話說的攻擊則由 LLM 護欄擋下，兩層互補
- 免費額度是目前最大的限制，大量測試時會觸發，已以多模型備援與「未計分」機制處理

## 九、得標行情初步發現

以 197 筆決標資料（決標日期 2026/03～2026/10）統計：

| 產業 | 樣本 | 平均決標價占預算 | 平均投標家數 |
|---|---|---|---|
| 資訊軟體 | 97 件 | 95.4% | 1.4 家 |
| 行銷設計 | 50 件 | 98.7% | 1.5 家 |
| 顧問研究 | 32 件 | 98.2% | 1.3 家 |
| 教育訓練 | 22 件 | 96.9% | 1.3 家 |

**解讀**：多數政府標案只有 1～2 家廠商投標，而且大多以接近預算的價格得標。對中小企業而言，主要障礙不是競爭，而是資訊取得。這正是本系統想解決的問題。（樣本仍持續每日累積中。）

## 十、開發過程中的問題與改進

| 遇到的問題 | 原因 | 改進方式 |
|---|---|---|
| 產業判斷誤差大 | 標題關鍵字太寬鬆 | 改用政府標準「標的分類代碼」 |
| 補助新聞混入無關報導 | 新聞搜尋結果雜 | 標題必須含「補助、獎勵、津貼…」等字 |
| 模型抄錯長網址 | LLM 逐字抄寫長字串不穩定 | 連結代碼機制，由程式還原網址 |
| 免費額度很快用完 | 一則對話需要 3～5 次模型呼叫 | 多模型分攤與備援、當日額度用完的模型自動跳過 |
| 採購網連線被拒 | 政府憑證不符合新版 Python 的嚴格檢查 | 保留憑證驗證，只關閉嚴格模式 |
| 網路斷線被誤判成「沒資料」 | 錯誤處理沒有區分情況 | 連線錯誤直接回報，失敗過多的日期不標記完成 |
| 向量 RAG 無法處理條件查詢 | 預算、截止日需要精確比較 | 改用 tool calling＋SQL |

## 附錄：執行方式

```bash
pip install -r requirements.txt
# 將 .env.example 複製為 .env，填入 Gemini API key
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

打開 http://localhost:8000 → 註冊帳號 → 開始使用。第一次啟動會自動載入專案附帶的初始資料（`seed/seed.db`，僅含公開資料），之後每天自動更新。
