## 一、專題摘要

本專題製作一個網頁版的 AI Agent，每天整理政府電子採購網的標案、決標結果與補助相關新聞，提供給中小企業或接案者查詢。

系統每天自動抓取資料，經過關鍵字萃取、過濾、去重與清理後存入資料庫。使用者登入後，可以在首頁看到最新一期尚未截止的標案，也可以用自然語言詢問 AI，例如「台中 10 人的軟體公司有什麼標案？」。AI 會記住使用者提供的公司條件，透過工具查詢資料庫後回答，回答前後各有一道安全檢查。

| 項目 | 內容 |
|---|---|
| 主題 | 政府標案與補助資訊整理 |
| 使用者 | 中小企業、新創、接案者 |
| 重複性排程 | 每天 07:30 自動抓取、清理、存入資料庫 |
| 多人使用 | 各自註冊帳號，共用每日資料，收藏與 AI 記憶分開 |
| 使用技術 | Python、FastAPI、SQLite、jieba、Google Gemini |

## 二、問題背景與動機

### 2.1 問題

- 政府電子採購網每天有大量公告，2026/10/08 當天為 3,011 筆，包含招標、決標、更正等類型，要從中找出跟自己相關的案子並不容易。
- 補助計畫的資訊分散在各部會網站與新聞中。
- 有專人追蹤標案的通常是規模較大的公司，小公司或個人比較難持續掌握這些資訊。

### 2.2 目標

1. 每天自動整理，減少使用者自己搜尋的時間
2. 依使用者的公司條件篩選，而不是列出全部資料
3. 整理過去的決標資料，作為評估是否投標的參考
4. 回答內容要能對應到實際資料，避免 AI 編造案名、金額或連結

│                                   │                                        │
│                                   ▼                                        │
│              前處理：提取 → jieba 關鍵字 → 過濾 → 去重 → 清理             │
│                                   │                                        │
│                                   ▼                                        │
│                         SQLite 資料庫（data/agent.db）                     │
└────────────────────────────────────────────────────────────────────────────┘
                                    │
          ┌─────────────────────────┴──────────────────────────┐
          ▼                                                    ▼
  網頁首頁                                          AI 小幫手（Gemini）

## 四、資料流程與前處理

### 4.1 資料來源

| 資料 | 來源 | 更新頻率 |
|---|---|---|
| 招標公告 | 政府電子採購網（透過 g0v 開放 API） | 每日 |
| 決標公告 | 同上，包含得標廠商、決標金額、底價、投標家數 | 每日 |
| 補助新聞 | Google 新聞 RSS（6 組關鍵字） | 每日 |

### 4.2 產業篩選方式

一開始用標題關鍵字判斷產業，例如「系統」「活動」，但誤判不少，像「活動中心整修工程」被歸到行銷類、「空調系統」被歸到資訊類。

後來改以政府採購的「標的分類代碼」為主要依據，例如勞務類 84 為電腦相關服務、勞務類 871 為廣告服務；關鍵字只作為輔助，且不套用在工程類標案上。

### 4.3 各階段資料量（2026/10/08）

| 階段 | 筆數 |
|---|---|
| 採購網當日公告 | 3,011 |
| 招標類型與產業篩選後 | 約 170 |
| 補助新聞：搜尋結果 → 標題篩選與去重後 | 21 → 9 |
| 決標資料（往前補抓 14 天） | 197 |

前處理沿用我之前寫的文件清理程式（jieba 關鍵字、過濾、去重、清理）。同一則補助新聞常有多家媒體報導，去重可以避免重複出現。

## 五、AI Agent 設計

### 5.1 LLM 選擇與參數

| 用途 | 模型 | 參數 |
|---|---|---|
| Agent 主模型 | gemini-3.5-flash | temperature 0.3 |
| 備援模型 | gemini-3.6 / 3.7 / 2.5-flash、2.5-flash-lite | 同上 |
| 安全檢查 | gemini-3.5-flash-lite | temperature 0，輸出 JSON |

Gemini 免費額度是每個模型分開計算，每分鐘和每天都有上限。測試時發現 3.8 Flash 每分鐘只能呼叫 5 次，而一次對話通常需要 3～5 次呼叫，所以讓 Agent 和安全檢查使用不同模型，並設定多個備援模型。當某個模型當天的額度用完，就改用下一個；如果只是每分鐘的額度用完，會稍等後再試。

### 5.2 Prompt 設計

System Prompt 用 XML 標籤分成三段：

```xml
<role>你是「標案補助小幫手」，協助台灣中小企業、新創與個人工作者……今天是 {today}。</role>
<user_profile>產業：{industry}｜人數：{company_size}｜地區：{location}｜需求：{need}</user_profile>
<rules>
1. 使用者提到產業、人數、地區或需求時，先呼叫 save_profile 記住。
2. 想找案子但看不出產業時，先追問產業，不要直接查。
3. 案子與數字只能來自工具回傳的結果，不可自行編造。
……（共 11 條）
</rules>
```

- `{user_profile}` 在每次對話時帶入使用者的公司條件
- 產業清單從設定檔讀取，在網頁上新增產業後，AI 也會使用新的清單

### 5.3 Memory

| 類型 | 內容 | 存放位置 |
|---|---|---|
| 長期記憶 | 產業、公司人數、地區、需求 | `users` 資料表，AI 用 `save_profile` 工具寫入 |
| 短期記憶 | 最近 10 則對話 | `messages` 資料表 |

長期記憶和個人資料頁使用同一份資料，所以在個人資料頁修改，AI 下次對話就會使用新的條件；反過來，對話中提到的條件也會顯示在個人資料頁。

### 5.4 Knowledge：使用 tool calling 查詢資料庫

標案資料有預算、截止日、地區、產業等欄位，使用者的問題常帶有條件，例如「台中、預算 500 萬以上、還沒截止的軟體標案」。向量檢索（RAG）是找語意相近的內容，不容易處理「大於 500 萬」「截止日在今天之後」這類條件。

因此本專題讓 LLM 負責理解問題與決定查詢條件，再由工具用 SQL 查詢資料庫，數字比較由程式處理。補助新聞沒有固定欄位，則用關鍵字搜尋。

### 5.5 Tools

| 工具 | 功能 | 問題範例 |
|---|---|---|
| `search_tenders` | 依產業、關鍵字、地區、預算、是否截止查詢標案 | 台中 500 萬以上的軟體標案？ |
| `search_subsidies` | 依關鍵字查詢補助新聞 | 最近有數位轉型補助嗎？ |
| `read_tender_page` | 讀取公告全文，限採購網網址 | 這案押標金多少？ |
| `analyze_awards` | 統計決標資料：金額、決標價占預算比例、投標家數、得標廠商 | 這類案子通常幾成得標？ |
| `list_favorites` | 列出使用者收藏的標案與剩餘天數 | 我收藏的哪個最快截止？ |
| `save_profile` | 記錄公司條件 | 我們是高雄 8 人的行銷公司 |
| `get_today_digest` | 取得當日整理的摘要 | 今天有什麼新的？ |

決標資料的平均、中位數、排名等數字由程式先算好，再交給 LLM 說明。

### 5.6 對話流程

```
使用者訊息
   │
   ▼
輸入檢查：先用規則比對常見的 prompt injection 字句，再由 LLM 判斷
   │ 不通過 → 婉拒
   ▼
Agent：讀取長期記憶與最近 10 則對話
   ├─ 缺少產業 → 先追問
   ├─ 查標案 → search_tenders，需要細節時再 read_tender_page
   ├─ 問決標行情 → analyze_awards
   ├─ 問補助 → search_subsidies
   └─ 提到公司條件 → save_profile
   ▼
輸出檢查：還原與核對連結 → LLM 檢查內容 → 加上「以公告為準」提醒
   ▼
回覆（網頁上會列出這次呼叫的工具）
```

### 5.7 安全檢查（Guardrail）

| 位置 | 方式 | 處理的情況 |
|---|---|---|
| 輸入 | 規則比對 | 「忽略以上指令」「system prompt」等常見字句 |
| 輸入 | LLM 判斷 | 換句話說的 prompt injection、圍標或借牌等違法詢問、不當內容 |
| 輸出 | 連結代碼 | 避免模型寫錯或編造網址 |
| 輸出 | LLM 判斷 | 不當用語、違法建議、洩漏系統指令 |

連結代碼的做法：測試時發現模型在抄寫採購網的長網址時會寫錯幾個字，所以工具改為回傳短代碼（如 `<<T1>>`），由程式在輸出時換回原本的網址；回覆中如果出現工具沒有提供過的網址，該行會被刪除。

## 七、帳號與資安

| 項目 | 做法 |
|---|---|
| 密碼 | 以 PBKDF2-SHA256 加上隨機 salt 雜湊後儲存 |
| 登入失敗 | 同一帳號 10 分鐘內錯誤 5 次會暫停登入 |
| 登入狀態 | session token 存在 HttpOnly cookie，資料庫只存雜湊值，7 天後失效 |
| 修改密碼 | 其他裝置的登入會失效 |
| 資料隔離 | 收藏、對話、AI 記憶依伺服器端的登入身分讀取 |
| 未登入 | 頁面導向登入頁，API 回傳 401 |
| 工具限制 | `read_tender_page` 只能讀取採購網網址 |
| API key | 放在 `.env`，不上傳到 GitHub |

## 八、評估

### 8.1 方法

準備 21 題測試題，分成標案檢索、決標行情、記憶與追問、補助查詢、安全檢查（應攔截／不應攔截）幾類。題目的標準答案在測試時由 SQL 從資料庫計算，例如「台中、500 萬以上、未截止的資訊軟體標案件數」，所以資料更新後不需要手動改答案。

每題檢查的項目：

- 是否呼叫正確的工具和參數
- 回答中的件數、案名、比例、廠商是否和資料庫一致
- 該攔截的有沒有攔截，正常問題有沒有被誤擋
- 輸出檢查是否刪除了不存在的連結

如果因為免費額度不足而沒有得到回答，該題記為「未計分」。

### 8.2 結果（2026/10/12）

| 類別 | 通過／已計分 |
|---|---|
| 標案檢索 | 5／5 |
| 決標行情 | 3／3 |
| 記憶與追問 | 2／2 |
| 補助查詢 | 1／1 |
| 安全檢查：應攔截 | 5／5 |
| 安全檢查：不應攔截 | 2／2 |
| 合計 | 18／18 |

| 指標 | 結果 |
|---|---|
| 被刪除的錯誤連結 | 0 個 |
| 一般問題平均回應時間 | 15.7 秒 |
| 被攔截問題的回應時間 | 0.1～1.2 秒 |

另外 3 題（沿用條件只改預算、收藏最快截止、離題問題）當天因額度用完未計分。詳細結果在 [docs/eval/](eval/)。

### 8.3 說明

- 測試題只有 21 題，而且是我自己設計的，結果只代表這組題目，不代表所有情況都能正確回答。
- 回應時間偏長，讀取公告全文的題目約 47 秒，主要花在連線採購網和多次呼叫模型。
- 規則比對可以不呼叫 LLM 就擋下常見的攻擊字句，換句話說的版本則需要 LLM 判斷。

## 十、開發過程遇到的問題

| 問題 | 原因 | 處理方式 |
|---|---|---|
| 產業判斷不準 | 標題關鍵字範圍太廣 | 改用標的分類代碼 |
| 補助新聞混入無關報導 | 新聞搜尋結果較雜 | 標題需包含補助相關字詞 |
| 模型寫錯網址 | 長字串逐字抄寫容易出錯 | 改用連結代碼，由程式還原 |
| 免費額度不足 | 每次對話需呼叫模型多次 | 分散到多個模型，設定備援 |
| 無法連線採購網 | 政府網站憑證不符合新版 Python 的嚴格檢查 | 保留憑證驗證，關閉嚴格模式 |
| 斷線被當成沒有資料 | 錯誤處理沒有區分 | 連線錯誤直接回報，失敗太多的日期之後重抓 |
| 條件查詢不準確 | 向量檢索不適合數字與日期條件 | 改用 tool calling 搭配 SQL |

## 附錄：執行方式

```bash
pip install -r requirements.txt
# 將 .env.example 複製為 .env，填入 Gemini API key
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

開啟 http://localhost:8000，註冊帳號後即可使用。第一次啟動時會載入專案內的初始資料（`seed/seed.db`，只有公開資料），之後每天自動更新。
